# 爬虫优化方案分析 + 安卓虚拟机可行性

> 2026-10-31　全部结论基于本机实测，不是推演。

## 一、安卓虚拟机：**不可行**，四条硬约束

| 项 | 实测值 | 结论 |
|---|---|---|
| Hyper-V 状态 | `已检测到虚拟机监控程序` | Hyper-V **已占用**虚拟化层 |
| `VMMonitorModeExtensions` | `False` | WMI 读不到 VT 扩展 |
| `SecondLevelAddressTranslationExtensions` | `False` | 读不到 SLAT |
| VBS（核心隔离） | `2` = 已启用 | 内存完整性在跑，进一步锁死虚拟化 |
| 可用物理内存 | **1.8 GB** | 模拟器最低要求 4GB 专留 |
| 磁盘 | C:46G / E:574G | 磁盘够，但不是瓶颈 |
| WSL | 未安装任何发行版 | 无 Linux 后备 |

**根本原因**：Hyper-V + VBS 已经占住了 AMD-V，安卓模拟器（BlueStacks / LDPlayer / MuMu / Genymotion）
要么抢不到硬件加速只能软解（慢到不可用），要么直接启动失败。**关掉 Hyper-V 才能跑**，
但你机器上 WSL、Docker 类功能可能依赖它，且重启后需重新配置。

**更关键的一点：就算跑起来也不划算。**
模拟器里跑的是淘宝/京东 App，采数据要额外装 Xposed/Frida 做 hook，
内存 1.8GB 的余量根本撑不住「模拟器 + App + hook 框架」。
投入产出比远低于直接改现有 Playwright 链路。

## 二、裸 HTTP 接口：**全部被封**，已实测

| 尝试 | 结果 | 含义 |
|---|---|---|
| PDD `proxy/api/search` 直连 POST | `403` / `error_code 40001` | 必须带 anti_content + AccessToken |
| 淘宝 `h5api.m.taobao.com` mtop | `RGV587_ERROR::SM 被挤爆啦` | 需要 `sign` 签名，裸调必拒 |
| 京东 `api.m.jd.com` | `{"code":"1","echo":"required string parameter 'appid'"}` | 需要 appid + 签名 |
| 京东 `item.m.jd.com/product/xxx.html` | `200` ✅ | **唯一通的**：移动端商品页可直读 |
| 京东 `so.m.jd.com` 搜索 | `302` 跳登录 | 搜索接口封死 |

**结论**：三家搜索接口都需要动态签名，签名的生成逻辑埋在混淆过的 JS 里。
与其逆向三套签名（淘宝 sign / 京东 sign / PDD anti_content），不如用浏览器让页面自己算 ——
这正是我们现在 `pdd_api` 里 `_capture_request` 的思路，方向是对的。

## 三、真正值得做的优化（按性价比排序）

### ✅ 1. 登录态复用与预热（几乎零成本，收益最大）
- 现在每次采集都新开 Session → 每次都重新握手 cookie、重新过风控探测
- **优化**：一个平台一次采集只开一次 Session（已经是），但**跨任务复用**还做不到
  —— 可以加「Session 保活池」：采集结束后不关浏览器，保活 N 分钟供下次复用
- 收益：省掉每次 ~3-8 秒的浏览器冷启动 + 首屏风控探测

### ✅ 2. 请求节奏自适应（已部分实现，可再进一步）
- 现在 `PLATFORM_PACING` 是**静态配置**（京东固定 10-22s）
- **优化**：改成**根据限流历史动态调整** —— 已被限过一次就把间隔乘 1.5，
  连续两次乘 2.5，采成 5 次无异常再逐步回落
- `cooldown.json` 里已有 `hits` 计数，扩展成"间隔系数"即可，改动很小
- 收益：不被封的前提下尽可能快

### ✅ 3. 京东走移动端商品页（实测 200，可直接用）
- PC 搜索页被封，但 `item.m.jd.com/product/<sku>.html` 返回 200
- **优化**：京东改用移动端 UA + 移动版商品页定价，搜索走 `so.m.jd.com` 的登录态
- 收益：京东从「几乎采不到」变成「至少能定价」

### ✅ 4. 缓存层：商品详情页短期缓存
- 同一商品 1 小时内价格基本不变，但我们现在每次都重新抓
- **优化**：加 `data/cache/` 按 `(platform, item_key)` 缓存 SKU 解析结果，
  有效期 30-60 分钟；命中就跳过详情页
- 直接解决「详情页补读拖垮采集」的老问题（配合默认关闭的 SKU_REPRICE，可以安全开启）

### ✅ 5. 失败重试的退避策略
- 现在详情页失败直接跳过，但没区分"临时网络抖动"和"被风控"
- **优化**：错误分类 —— `ERR_NETWORK_CHANGED`/`Timeout` 重试 1 次；
  `403`/`error_code` 直接判风控、不重试并记冷却

### 🔶 6. 多出口 IP（成本高，非必需）
- 本机出口实测有两个不同 IP（广东广电 124.240.71.19 / 美国 142.249.36.59），
  说明代理链路在切换 —— 这个**不确定性本身就是风险**（淘宝看到 IP 跳变会加重风控）
- **建议**：先固定单出口（直连或固定代理），反而比"多 IP 轮换"更安全

### 🔶 7. 安卓路线的正确形态：不用模拟器，用真机
如果确实要 App 数据：
- **真机 + adb + uiautomator2**（本机已装 `adb`，`appium` 3.9.0 也在）
- 手机连 USB，用 uiautomator2 驱动淘宝/京东 App 搜索页，读屏幕上的商品列表
- 优点：App 接口不受网页风控约束；缺点：单机慢、需要手机常连
- **这条比模拟器实际得多**，但工程量大，不建议现在做

## 四、明确的取舍

| 方案 | 可行性 | 建议 |
|---|---|---|
| 安卓模拟器 | ❌ 不可行（Hyper-V 占用 + 内存不足） | 放弃 |
| 真机 + uiautomator2 | ✅ 可行 | 备选，工程量大 |
| 裸 HTTP 接口 | ❌ 三家都要签名 | 放弃 |
| 浏览器上下文发请求（现状） | ✅ 已通 | 保持并强化 |
| 京东移动端商品页 | ✅ 实测 200 | **优先做** |
| 节奏自适应 / 缓存 / 退避 | ✅ 改动小 | **优先做** |

## 五、下一步动手顺序

1. **节奏自适应**（改 `pacing()` 用 `cooldown.hits` 调系数，~30 行）
2. **SKU 详情页缓存**（新增 `data/cache/`，让 SKU_REPRICE 能安全打开）
3. **京东移动端定价**（`PLATFORMS["jd"]` 换移动 UA + 商品页 URL）
4. Session 保活池（可选，收益中等）
5. 真机 uiautomator2（远期）
